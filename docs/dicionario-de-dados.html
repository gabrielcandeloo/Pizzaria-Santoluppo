Dicionário de Dados Conceitual (Preliminar)

Pizzaria Santoluppo

1. Modelo conceitual

Este modelo representa uma pizzaria que opera exclusivamente via delivery e retiradas no balcão. Cada cliente é identificado no sistema, possui endereços cadastrados para despacho, e realiza pedidos vinculados aos produtos do cardápio mediante a inserção de códigos numéricos. Ao final, o acerto financeiro é registrado com a segmentação da forma de pagamento.

EntidadeRelaciona-se comCardinalidade
CLIENTEENDERECO (Possui)1:N — um cliente pode possuir múltiplos endereços cadastrados ao longo do tempo (ex: casa, trabalho).
CLIENTEPEDIDO (Faz)1:N — um cliente realiza vários pedidos; cada pedido pertence estritamente a um único cliente.
PEDIDOPRODUTO (Contém)N:N — um pedido agrupa vários produtos; um produto é listado em vários pedidos. Esse relacionamento dá origem à entidade associativa física ITEM_PEDIDO, portadora de quantidade e preço.
PEDIDOPAGAMENTO (Gera)1:1 — um pedido finalizado gera a consolidação de um montante total a ser pago.
PAGAMENTOFORMAS_PAGAMENTOS (Decisão)N:N — um pagamento pode ser dividido em mais de uma forma (ex: metade dinheiro, metade PIX), e uma forma quita múltiplos pagamentos diários.

Neste modelo conceitual, o relacionamento N:N "Contém" entre PEDIDO e PRODUTO foi destacado com atributos próprios de quantidade e preço unitário, caracterizando uma entidade associativa implícita que garantirá o histórico financeiro na modelagem lógica.

Cliente é o consumidor final, identificado unicamente no sistema para garantir o direcionamento da entrega.

Endereço é o local geográfico exato associado ao cliente para o despacho da mercadoria.

Pedido é a transação central, que agrupa os itens solicitados, o status de entrega e possíveis cancelamentos.

Produto é o item do cardápio unificado (pizzas, brotos e bebidas), identificado por um código numérico memorizado pela operação.

Pagamento é a consolidação monetária gerada ao final da elaboração do pedido.

Formas de Pagamento é a segmentação categórica (Dinheiro, PIX, Cartões) exigida para o fechamento diário do caixa.

2. Fluxo de dados (visão de DFD)

Cliente aciona a pizzaria → é consultado ou cadastrado em CLIENTE e seu ENDERECO é confirmado → o operador abre um PEDIDO associado ao cliente → os itens solicitados são inseridos de forma ágil utilizando o código do PRODUTO, registrando a quantidade e valor (ITEM_PEDIDO) → o pedido é encaminhado para a produção → caso ocorra desistência antes do preparo, a justificativa é gravada no atributo de cancelamento do pedido sem afetar o estoque → ao final, o total devido gera um PAGAMENTO vinculado às FORMAS_PAGAMENTOS utilizadas, viabilizando o fechamento do caixa no fim do expediente → os dados pessoais mantêm conformidade com a LGPD (§6).

3. Convenções do dicionário

SGBD: MySQL 8, mecanismo de armazenamento InnoDB — cuida da persistência dos arquivos de dados, do log de transações e mantém o índice primário.

Codificação de caracteres: utf8mb4 com collation utf8mb4_0900_ai_ci. Escolhida por cobrir acentuação do português sem perda em campos textuais.

Notação formal (símbolos usados neste dicionário):

SímboloSignificado

Prefixos: NM_ nome, DT_ data, ID_ identificador (não sofre operação matemática), CD_ código de domínio, QT_ quantidade, TP_ tipo (categorização), IN_ indicador booleano, VL_ valor monetário, DS_ descrição/texto livre.

Versão deste dicionário: v1.0, Outubro de 2026. Atende ao princípio de rastreabilidade exigido pela LGPD.

4. Dicionário de dados por entidade

Cada atributo aparece com o nome padronizado lógico, o nome original utilizado no diagrama visual, a proposta de tipagem física e a marcação de chave primária (PK).

CLIENTE

CLIENTE = @ID_CLIENTE + NM_CLIENTE + DS_TELEFONE

Leitura: @ID_CLIENTE é o identificador único; os dois campos seguintes são obrigatórios e conectados por +. Entidade detentora de dados sensíveis (PII).

AtributoDescriçãoRegra de negócio associada
ID_CLIENTECódigo · integer · PKIdentificador sistêmico do cliente.Obrigatório; gerado pelo sistema.
NM_CLIENTENome · varchar(120)Nome do consumidor final.Obrigatório para identificação nominal do despacho.
DS_TELEFONETelefone · varchar(15)Número de contato com DDD.Obrigatório; canal de comunicação em caso de problemas com o delivery.

Índices: PK ID_CLIENTE (clusterizado); índice em DS_TELEFONE (busca rápida no atendimento).

ENDERECO

ENDERECO = @ID_ENDERECO + DS_RUA + NM_BAIRRO + (CD_CEP)

Leitura: @ID_ENDERECO é o identificador; DS_RUA e NM_BAIRRO são obrigatórios, enquanto CD_CEP é classificado como opcional ( ) para não travar o cadastro caso o cliente não o saiba decorado.

AtributoDescriçãoRegra de negócio associada
ID_ENDERECOCódigo (implícito) · integer · PKIdentificador do local de entrega.Obrigatório; gerado pelo sistema.
DS_RUARua · varchar(150)Logradouro e número da residência.Obrigatório para viabilizar a entrega física.
NM_BAIRROBairro · varchar(80)Bairro da entrega.Obrigatório; utilizado para possível roteirização do entregador.
CD_CEPCEP · varchar(8)Código Postal.Opcional; gravado apenas com números.

Índices: PK ID_ENDERECO.

PEDIDO

PEDIDO = @ID_PEDIDO + DT_HORA + DS_ENTREGA + (DS_CANCELAMENTO)

Leitura: (DS_CANCELAMENTO) é opcional porque um pedido só receberá este preenchimento caso a transação seja interrompida antes da produção.

AtributoDescriçãoRegra de negócio associada
ID_PEDIDONúmero · integer · PKNúmero sequencial do pedido.Obrigatório.
DT_HORAData e Hora · datetimeRegistro temporal de abertura.Obrigatório; gerado automaticamente pelo sistema.
DS_ENTREGAEntrega · varchar(30)Status do andamento logístico.Obrigatório.
DS_CANCELAMENTOCancelamento (0, 1) · varchar(255)Motivo da desistência.Opcional. É um texto livre; o preenchimento não engatilha devolução de estoque automático.

Índices: PK ID_PEDIDO; índice temporal em DT_HORA.

ITEM_PEDIDO (Relacionamento Associativo "Contém")

ITEM_PEDIDO = QT_ITEM + VL_UNITARIO

Leitura: Retrata a intersecção física resultante do relacionamento N:N entre pedido e produto.

AtributoDescriçãoRegra de negócio associada
QT_ITEMQuantidade · integerVolume solicitado do mesmo produto.Obrigatório; inteiro maior que zero.
VL_UNITARIOPreço Unitario · decimal(10,2)Preço cobrado no momento da venda.Obrigatório. Resguarda o histórico financeiro do caixa caso o valor base do cardápio seja alterado no futuro.

PRODUTO

PRODUTO = @CD_PRODUTO + NM_SABOR + [TP_PIZZA | TP_BROTO | TP_BEBIDA | TP_REFRIGERANTE] + (DS_TAMANHO) + VL_PRECO

Leitura: @CD_PRODUTO é chave primária, mas usa CD_ pois faz referência a um domínio memorizado pela operação (ex: 58 = mussarela). DS_TAMANHO é opcional (bebidas podem não ter tamanho mapeado).

AtributoDescriçãoRegra de negócio associada
CD_PRODUTOCódigo · integer · PKIdentificador numérico do cardápio.Obrigatório e único. Utilizado nativamente pelos operadores para inserir itens rapidamente.
NM_SABORSabor · varchar(100)Nome comercial do item.Obrigatório.
TP_CATEGORIACategoria · varchar(20)Classificação da natureza do produto.Obrigatório. Alternativas estritas: pizza, broto, bebida, refrigerante.
DS_TAMANHOTamanho · varchar(15)Proporção do item (P, M, G).Opcional.
VL_PRECOPreço · decimal(10,2)Valor tabelado atual do produto.Obrigatório; alimenta o item do pedido.

Índices: PK CD_PRODUTO.

PAGAMENTO

PAGAMENTO = @ID_PAGAMENTO + VL_TOTAL
AtributoDescriçãoRegra de negócio associada
ID_PAGAMENTOCódigo · integer · PKIdentificador do repasse financeiro.Obrigatório.
VL_TOTALvalor_total · decimal(10,2)Montante quitado.Obrigatório; consolidado a partir dos itens do pedido.

Índices: PK ID_PAGAMENTO.

FORMAS_PAGAMENTOS

FORMAS_PAGAMENTOS = @ID_FORMA + [TP_DINHEIRO | TP_PIX | TP_CARTAO]
AtributoDescriçãoRegra de negócio associada
ID_FORMACódigo · integer · PKID do método aceito.Obrigatório.
TP_METODODescricao_Metodo · varchar(30)Rótulo da forma de quitação.Obrigatório. Limitado às três vias de soma que a pizzaria utiliza (Dinheiro, PIX, Cartões).

Índices: PK ID_FORMA.

As entidades CLIENTE e ENDERECO concentram Informações de Identificação Pessoal (PII). O banco de dados se pauta pelo princípio da minimização, tratando os dados exclusivamente para permitir a efetivação das entregas, vedando a extração em massa. A exclusão real não é praticada nos registros de faturamento visando a estabilidade financeira e a auditoria de acessos.
